1

Análisis de Complejidad (Big-O)

rápido antes de escribirlo

Big-O mide cómo crece el tiempo cuando aumentan los datos. No es velocidad absoluta: clasifica el tipo de crecimiento.

Las 4 complejidades esenciales

ComplejidadNombreAnalogíaEn código
O(1)ConstanteAbrir en una página marcadaarr[0] · map[key]
O(n)LinealLeer un libro página por página1 for que recorre todo
O(n²)CuadráticaComparar cada libro con todos2 for anidados
O(log n)LogarítmicaDiccionario: mitad por mitadwhile (n > 1) { n = n ~/ 2; }

Pregunta clave: si duplicas n y el tiempo se duplica → O(n); se cuadruplica → O(n²); apenas cambia → O(log n); no cambia → O(1).

Regla del 10⁸ y tabla de constraints → complejidad

Un procesador ejecuta ~100 millones de operaciones/segundo. Si tu algoritmo supera eso → "Time Limit Exceeded".

Si el problema dice…Tu algoritmo debe ser…
n ≤ 10Cualquier cosa (backtracking / O(2ⁿ))
n ≤ 100O(n³) o mejor
n ≤ 5,000O(n²) o mejor (2 loops anidados)
n ≤ 10⁵O(n log n) o mejor (sorting / binary search)
n ≤ 10⁶O(n) o mejor (un solo recorrido)
n ≤ 10⁷O(n) con operaciones simples

Cómo analizar cualquier código: 3 patrones

Patrón en el códigoComplejidadSeñal
1 loopO(n)for (cada elemento) { hacer algo }
2 loops anidados (mismos datos)O(n²)for i { for j { … } }
while que divide por 2O(log n)while (n > 1) { n = n ~/ 2; }

Reglas de combinación: secuencial (uno tras otro) → toma la MÁS GRANDE · anidados → se MULTIPLICAN · constante dentro del loop → no cambia. O(n) + O(n²) = O(n²).

Operaciones O(1) vs O(n)

O(1)O(n) — ¡cuidado!
Suma, resta, módulo, comparaciónarr.contains(x) · arr.indexOf(x)
arr[i] · map[key] · set.contains(x)arr.insert(0, x) · arr.removeAt(i)
Asignar, imprimirList.from(arr) · arr.sublist()

Espacio y recursión

Complejidad espacial: array/map de n → O(n); recursión profunda → O(n) stack (puede causar stack overflow); variable auxiliar → O(1).

Si cada llamada hace…ComplejidadEjemplo
1 llamada recursiva con n-1O(n)Factorial
1 llamada recursiva con n/2O(log n)Binary search
2 llamadas recursivasO(2ⁿ) — lentoFibonacci sin memo
2 llamadas + ordenarO(n log n)Mergesort

Regla: recursión que parece loop (1 llamada) = O(n)/O(log n). Que parece árbol (2+ llamadas) = O(2ⁿ) o peor → necesita memoización.

Checklist pre-código: ¿cuál es el n máximo? · ¿qué complejidad necesito? · ¿mi enfoque cumple? · ¿puedo usar Map/Set para O(1)? · ¿necesito pre-computar? · ¿cuánto espacio extra uso?

Reconocimiento de Patrones

80% de los problemas · ~15 patrones

No inventes algoritmos: reconoce cuál patrón aplica. Framework de 3 pasos:

  1. Identificar tipo de input → patrones candidatos
  2. Detectar keywords del enunciado → patrón
  3. Validar contra las constraints → ¿cabe la complejidad?

Paso 3: Validación

¿La complejidad del patrón cabe en las constraints? (O(n²) cuando necesitas O(n) → mal patrón). ¿Cubre todos los edge cases? (con negativos, Sliding Window falla → usa Prefix Sum). ¿Hay uno más simple? (Greedy > DP si ambos funcionan).

El Mantra: "Este es un problema de [PATRÓN] porque el input es [TIPO] y me piden [QUÉ], con complejidad [O(?)]." Si puedes completarlo, estás listo para implementar.

Plantillas esenciales (condensadas)

// TWO POINTERS (array ordenado) — O(n) | O(1)
while (left < right) {
  int sum = arr[left] + arr[right];
  if (sum == target) return [left, right];
  else if (sum < target) left++;   // necesito más
  else right--;                     // necesito menos
}

// SLIDING WINDOW (tamaño variable, longest) — O(n)
int left = 0, maxLen = 0;
for (int right = 0; right < arr.length; right++) {
  // expandir: agregar arr[right] al state
  while (/* condición violada */) { left++; /* quitar arr[left] */ }
  maxLen = max(maxLen, right - left + 1);
}
// BFS (camino mínimo sin peso) — O(V+E) | O(V)
Queue<List<int>> queue = Queue();   // [node, dist]
Set<int> visited = {};
queue.add([start, 0]); visited.add(start);
while (queue.isNotEmpty) {
  var cur = queue.removeFirst();
  if (cur[0] == target) return cur[1];
  for (int nb in graph[cur[0]]) {
    if (!visited.contains(nb)) {
      visited.add(nb);
      queue.add([nb, cur[1] + 1]);
    }
  }
}
return -1; // sin camino

// DFS grid (contar islas) — O(rows×cols)
void dfs(Grid g, int r, int c) {
  if (fuera de rango || g[r][c] != '1') return;
  g[r][c] = '0'; // marcar visitado
  dfs(g, r+1, c); dfs(g, r-1, c); dfs(g, r, c+1); dfs(g, r, c-1);
}
// BINARY SEARCH — O(log n) | O(1)
while (left <= right) {
  int mid = left + (right - left) ~/ 2;
  if (arr[mid] == target) return mid;
  else if (arr[mid] < target) left = mid + 1;
  else right = mid - 1;
}
return -1;

// DP (Climbing Stairs) — O(n) | O(n)
List<int> dp = List.filled(n + 1, 0);
dp[1] = 1; dp[2] = 2;
for (int i = 3; i <= n; i++) { dp[i] = dp[i-1] + dp[i-2]; }
return dp[n];

// BACKTRACKING (permutaciones) — O(n!)
if (current.length == nums.length) { resultado.add(List.from(current)); return; }
for (int i = 0; i < nums.length; i++) {
  if (used[i]) continue;
  used[i] = true; current.add(nums[i]);   // hacer
  backtrack();                              // explorar
  current.removeLast(); used[i] = false;  // deshacer ← CLAVE
}

Reglas de pseudocódigo limpio

Recursión y Backtracking

recursión = llamarse · backtracking = deshacer

Recursión: los 3 pasos

  1. Caso base — ¿cuándo para? Sin esto, llamada infinita.
  2. Caso recursivo — ¿cómo reduces el problema?
  3. ¿Qué cambia en cada llamada? — algo debe acercarse al caso base.
int resolver(tipo input) {
  if (input es casoBase) return resultadoBase;  // 1. base
  return operacion(input, resolver(inputReducido)); // 2. recursivo
}

Memoización: evitar recalcular

Recursión con 2+ llamadas recalcula lo mismo (fibonacci = O(2ⁿ)). Con Map o @cache → O(n). Regla: si ves 2+ llamadas recursivas, necesitas memo.

Cuándo usar cada uno

SituaciónUsar
Dividir y conquistar (merge sort)Recursión simple
Explorar todas las combinacionesBacktracking
Subproblemas repetidosRecursión + memoización
Árboles binariosRecursión (DFS)

Backtracking = probar, y si no funciona, REVERTIR. Plantilla: ¿es solución? → agregar y return. Para cada candidato: si es válido → hacer · explorar · deshacer (el deshacer es la clave).

System Design Básico para Flutter

diseñar la app, no solo la función

Framework de 4 pasos

1Clarificarrequisitos + restricciones 2Diseñaralto nivel (componentes + datos) 3Profundizarmodelado + Flutter 4Escalar¿qué pasa con 1M usuarios?

Paso 1 — preguntas obligatorias: ¿cuántos usuarios? · ¿cuántos datos por día? · ¿latencia aceptable? · ¿requiere real-time (WebSocket vs polling)?

Paso 2 — componentes clave: Flutter app (cliente) → API (REST/WebSocket) → Backend (Supabase) → PostgreSQL → Cache (Redis / SharedPreferences).

Paso 4 — problemas comunes de escala

ProblemaSolución
Demasiadas consultasCaching (Redis, local)
Imágenes lentasCDN + compression
Real-timeWebSocket / Supabase Realtime
BD lentaÍndices + read replicas
Servidor saturadoLoad balancing

Ejemplo chat: tablas conversations · messages · conversation_members (PK compuesta) + suscripción con onPostgresChanges(PostgresInsertEvent) en ChatCubit → emite Message.fromJson(payload.newRecord).

Errores en entrevistas

✗ codificar sin clarificar · ✗ no mencionar escalabilidad (paso 4 siempre) · ✗ ignorar edge cases · ✗ solo REST cuando piden real-time (menciona WebSocket/Supabase Realtime).

Errores Comunes y Verificación

detectar en tiempo real
FaseError típicoSolución
EntenderNo leer todo el enunciado · asumir sin preguntarLeer 2 veces · preguntar edge cases · releer qué retorna (¿índices o valores?)
ApproachBrute force sin pensar · over-engineering · ignorar restriccionesBuscar patrón primero · solución más simple · ver límites antes de diseñar
ImplementarOff-by-one · índice inválido · olvidar edge cases · no deshacer en backtrackingDibujar caso base · verificar bounds · testear vacío/1/2 · siempre deshacer()
VerificarSolo mirar el código · solo happy path · "se ve bien"Dry run con el ejemplo · probar vacío/1/máximo · trazar paso a paso

Regla de los 3 casos: 1) vacío/null → ¿no crashea? · 2) mínimo (1 elem) → ¿funciona? · 3) normal (ejemplo) → ¿retorna correcto?

// Errores clásicos en Dart
arr[0];                 // ✗ crash si vacío → arr.isEmpty ? null : arr[0]
map[key]!;              // ✗ crash si falta → map[key]  (null si no existe)
n * factorial(n - 1);   // ✗ sin caso base → infinito
backtrack(...);         // ✗ olvidar deshacer → actual.removeLast()

Checklist antes de decir "estoy listo": ¿leí TODAS las restricciones? · ¿probé el ejemplo del enunciado? · ¿probé edge cases (vacío, 1 elem, null)? · ¿la complejidad cumple? · ¿el retorno es correcto? · ¿compila en Dart?
