Estrategia de versionado

caret · pinning · lockfile

Lockfile

  • Apps: pubspec.lock se comitea → todos usan versiones exactas.
  • Librerías: no se comitea; cada consumidor resuelve.
  • Conflicto de merge: correr dart pub get reconstruye el lockfile.

Overrides (temporales)

dependency_overrides: en pubspec.yaml fuerza una versión cuando dos paquetes chocan. Desde Dart 3.8 existe pubspec_overrides.yaml (no se comitea, va en .gitignore) para overrides de desarrollo. Ambos son parches: el objetivo es que el mantenedor upstream actualice su constraint.

Regla de oro: caret para librerías · pinning exacto para frameworks críticos · SHA para Actions · y dart pub deps como herramienta de diagnóstico de conflictos.

Flujo de actualización

outdated · upgrade · fix · test
Columna pub outdatedSignificado
CurrentLo que tienes instalado
UpgradableMáximo con dart pub upgrade (patch/minor)
ResolvableMáximo que pub resuelve sin tocar pubspec.yaml
LatestÚltima publicada (puede ser major)

Proceso seguro

1. Leer CHANGELOG + migration guide
2. dart pub upgrade <paquete>
3. dart pub outdated   (verificar)
4. dart fix --apply    (migraciones del SDK)
5. flutter analyze
6. flutter test -j 1
7. build_runner: dart run build_runner build --delete-conflicting-outputs
8. Commit separado semántico: fix(deps): update supabase_flutter to 2.17.2

dart pub upgrade --major-versions modifica pubspec.yaml. ⚠️ Un paquete a la vez, nunca todos juntos. Equivalente npm: npm outdated → npm update → npm install next@latest → npm audit.

Revisar por paquete: supabase_flutter (inicialización), flutter_bloc (BlocObserver), fpdart (Either/TaskEither), go_router (ShellRoute/redirect), dio (interceptors/multipart), isar_community (regenerar .g.dart).

2

Automatización: Dependabot y Renovate

bots de actualización

Dependabot — YAML simple, ideal para empezar. Ecosistemas del monorepo: github-actions (/), npm (apps/web), pub (apps/mobile), schedule weekly, límite 5–10 PRs.

Grupos (desde 2023): agrupa familias (bloc, flutter_bloc, bloc_test) o patch updates en un solo PR. Nunca agrupes majors.

Renovate — más potente: extends: ["config:recommended"], groupName, schedules por paquete, dashboard, onboarding. Útil cuando necesitas control fino.

Auto-merge (recomendación oficial GitHub)

dependabot/fetch-metadata@v3  →  outputs.update-type
gh pr merge --auto --squash "$PR_URL"   (solo patch/minor que pasen CI)

Auditoría semanal: workflow con cron que corre dart pub outdated --no-dev, detecta atrasadas y crea un issue automático con actions/github-script@v9. Revisión manual SIEMPRE para majors.

4

Seguridad y auditoría

OSV · npm audit · CVSS
  • Árbol: dart pub deps --json + jq para extraer dependencias directas.
  • CVE conocidas: OSV.dev API (POST /v1/query, ecosistema Pub) y GitHub Advisory Database.
  • Web: npm audit / npm audit --audit-level=high / --json para CI.
  • Dependabot security updates: PRs automáticos por CVE (Settings → Code security).

Matriz de respuesta CVSS

SeveridadAcciónPlazo
Critical (9.0–10.0)Actualizar ya · parche manual si no hay fix< 24h
High (7.0–8.9)Próximo ciclo de trabajo< 1 semana
Medium (4.0–6.9)Próximo sprint< 1 mes
Low (0.1–3.9)Documentar · revisión trimestral< 3 meses

Gate en CI: por cada paquete del árbol (nombre@versión) consulta OSV.dev; si hay vulns, falla el build. Es lo que convierte la auditoría en algo reactivo, no manual.

5

Deprecación, EOL y migraciones

banderas rojas · ADR

Señales: sin commits >12 meses, issues sin respuesta, paquete que no soporta la última Dart, dependencias obsoletas en cadena (heurística, no regla formal). Ejemplos reales: hive → isar_community, pennylane → fpdart, built_value → freezed/json_serializable, dartson → json_serializable.

Proceso de migración

Investigar alternativa → rama separada → capa de compatibilidad (wrapper)
→ migración gradual (feature flags, un módulo a la vez)
→ dart pub remove <paquete> → tests completos → ADR + guías del equipo

EOL de Flutter/Dart

Solo la última stable (3.47.0) tiene soporte activo garantizado; 3.44.0 es la anterior. Sin parches de seguridad garantizados para versiones viejas. Cadencia ~3 meses entre releases.

Tras actualizar la constraint del SDK (sdk: ^3.13.0), corre dart fix --apply. Documenta cada reemplazo como ADR (contexto, decisión, consecuencias). Objetivo del monorepo: nivel Gold (Flutter stable + paquetes en minor más reciente).

Operación continua: Makefile y CI

auditoría automatizada
Target / workflowQué hace
make auditAuditoría completa: mobile (pub deps --json) + web (npm audit) + Actions sin pin
make dep-reportReporte markdown del estado de dependencias
make check-constraintsDetecta conflictos y dependency_overrides no temporales
make dep-tree / deps-securityÁrbol completo / escaneo OSV por paquete
CI semanalcron + flutter-action@v3 (3.47.0) + setup-node@v7 (24); crea issue si hay atrasadas
Gate en PRsBloquea si hay high/critical en npm audit o dependency_overrides persistentes

Checklist

  • Por PR: analyze sin errores, CI verde.
  • Semanal: make audit, mergear patch/minor que pasen CI.
  • Mensual: make dep-report, issues de seguridad, lockfiles al día.
  • Trimestral: paquetes deprecados, nueva stable de Flutter, docs.
  • Anual: auditoría completa, EOL de Node, Flutter 2+ releases atrás.

Madurez: estos targets convierten el mantenimiento de rutina en algo automático, medible y con dueño en el equipo.
