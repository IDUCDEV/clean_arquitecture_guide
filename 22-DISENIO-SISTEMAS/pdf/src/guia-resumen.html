1

Estimación de Escala

back-of-the-envelope

Antes de dibujar el diagrama, calcula qué tanto debe aguantar. Estos números guían todas las demás decisiones (cache, replicas, sharding).

Las 4 fórmulas

MétricaFórmulaEjemplo (feed)
QPS lecturasusuarios activos × acciones/usuario ÷ segundos10M MAU · 5% pico · 100 lecturas/día → ~1.7K QPS
QPS escriturasacciones/día ÷ 86,4001.5M posts+likes/día → ~17 QPS
Storagefilas × bytes × retenciónMedia del feed → ~2.7 TB/año
Ratio L/Electuras ÷ escrituras~10:1 → sistema read-heavy

Lectura del ratio: ratio 10:1 → read-heavy → el cuello de botella son las lecturas → cache + read replicas. Ratio cercano a 1 o mayor en escrituras → write-heavy → el cuello es la DB → particionado/colas.

Latencia vs throughput: latencia = tiempo de una acción; throughput = acciones por segundo. Problema de latencia = "lento para uno". Problema de throughput = "rápido para uno, se hunde con muchos". Objetivo: maximal throughput con latency aceptable.

2

Modelado de Datos

el primer cuello de botella

SQL vs NoSQL

CriterioSQL (PostgreSQL/Supabase)NoSQL
EsquemaFijo, relacionalFlexible
Transacciones ACIDSólidasVariables
Relaciones/joinsNativosSe emulan en la app
EscaladoVertical + réplicas; sharding manualHorizontal por diseño
CuándoCasi siempre (empieza aquí)Latencia extrema, KV, datos no estructurados

Regla práctica: empieza con RDBMS. Postgres (corazón de Supabase) cubre el 90% con JSONB, RLS y realtime.

Índices

Aceleran lecturas pero frenan escrituras y consumen espacio. Se crean para los path de acceso reales, no para todo.

CREATE INDEX idx_posts_user ON posts (user_id);
CREATE INDEX idx_posts_user_created ON posts (user_id, created_at DESC);

Replicación (más lecturas + tolerancia)

TipoQuién escribeTrade-off
Master-SlaveSolo el master; slaves leenEscrituras pueden tener lag (eventual consistency)
Master-MasterAmbos escribenConflictos entre masters — complejo, evitar al inicio

Sharding (último recurso)

Dividir la tabla en N bases por un shard key (ej. Hash(user_id) % N). Escala escrituras/storage pero rompe joins y complica rebalanceo. Orden: índices → cache → réplicas → federación → sharding.

Denormalización

Duplicar data a propósito para leer sin joins. Leer es rápido, pero cada escritura debe mantener las copias sincronizadas (riesgo de inconsistencia).

NormalizadoDenormalizado
EscrituraSimple (1 lugar)Compleja (mantener copias)
LecturaJoins carosRápida (todo en la fila)

Árbol de decisión: ¿consulta lenta? → índices + EXPLAIN → ¿lectura repetitiva? → cache → ¿mucha concurrencia? → read replicas → ¿escrituras el cuello? → particionado → ¿nada funciona? → sharding.

3

Cache y Rendimiento

la herramienta #1

Dónde cachear (de cerca a lejos del usuario)

AppIsar local, HTTP cache CDNmedia, estáticos Serverrespuestas HTTP/Edge DBquery cache, views

Las 4 estrategias de actualización

EstrategiaQué haceTrade-off
Cache-aside (lazy)Miss → lee DB → guarda en cachePrimer acceso lento; cachea solo lo usado ✅ recomendada
Write-throughEscribe cache + DB juntosLecturas siempre frescas; escrituras más lentas
Write-behindEscribe cache, persiste asyncEscrituras rapidísimas; riesgo de pérdida
Refresh-aheadRefresca antes de expirarMenos misses; puede predecir mal

TTL: tiempo de vida — mientras no expire el dato puede estar stale. Invalidación: cuando el dato cambia, hay que actualizar el cache (o el usuario ve data vieja). Eviction: LRU (Least Recently Used) es lo estándar.

Cache stampede (miss storm): si todos los caches expiran a la vez, miles pegan a la DB. Mitigación: jitter en TTL + stale-while-revalidate.

// Feed del repo (decisión completa):
Lectura:  app (Isar) → si miss → API → Redis → si miss → Postgres → cachea → devuelve
Escritura: crear post → invalida el cache del feed del autor (write-through)
Justificación: ratio 10:1 read-heavy → cache-aside + invalidación al escribir.
4

Realtime y Streaming

cuándo cada técnica

Las 4 opciones

TécnicaDirecciónCuándo
PollingCliente → servidorSegundos de latencia, simple (refrescar cada 30s)
Long pollingCliente mantiene la conexión hasta respuestaSin WebSocket, menos peticiones
WebSocketBidireccional full-duplexRealtime de verdad (chat, presencia)
SSEServidor → cliente (unidireccional)Updates solo del servidor

Asincronía (message/task queues)

Desacoplar el productor del consumidor: el mensaje espera si el consumidor cae. En Supabase: trigger en DB → Edge Function → notificación. Cuidado: si el consumidor va más lento, la cola crece (backpressure) — monitorear su tamaño.

Supabase Realtime (gestionado)

3 canales oficiales: Postgres Changes (recibe inserts/updates/deletes), Broadcast (mensajes entre clientes), Presence (quién está online).

Postgres ──(WAL)──▶ Realtime ──(WebSocket)──▶ Flutter App
supabase.channel('messages:room-1')
  .onPostgresChanges(event: insert, table: 'messages',
    callback: (payload) => emit(Message.fromJson(payload.newRecord)))
  .subscribe();

Árbol de decisión: ¿<1-2s? → polling · ¿unidireccional? → SSE · ¿bidireccional baja latencia? → WebSocket (Supabase Realtime) · ¿algo intermedio? → long polling.

5

Escalabilidad y Alta Disponibilidad

CAP · scaling · nueves

Performance vs Scalability

Performance: lento para un usuario. Scalability: rápido para uno, lento bajo carga. Escalar: primero vertical (más CPU/RAM, simple), luego horizontal (más máquinas, con load balancing).

CAP theorem (elegir 2 de 3)

Consistency · Availability · Partition tolerance. La red no es confiable → siempre hay particiones → eliges entre C y A.

CP (consistencia)AP (disponibilidad)
Ante particiónEspera/bloquea hasta estar consistenteResponde con lo disponible (puede estar viejo)
Ideal paraPagos, inventario, contadoresFeeds, chats, notificaciones

Patrones de consistencia

PatrónQué garantiza
WeakLos reads pueden no ver el write (best-effort)
EventualLos reads lo verán eventualmente (ms) — DNS, feeds, likes
StrongTodos los reads ven el write — RDBMS

Disponibilidad en números

DisponibilidadDowntime/añoDowntime/día
99%3d 15h14m 24s
99.9%8h 45m1m 26s
99.99%52m 35s8.6s

Failover: active-passive (standby, más barato) vs active-active (ambos atienden, riesgo de conflictos). Serie vs paralelo: componentes en serie multiplican la indisponibilidad; redundancia en paralelo la reduce.

En Supabase no reinventes la HA: Auth, DB, Storage y Realtime tienen SLA gestionado. Tu trabajo es: no crear puntos únicos de fallo en tu código, elegir el SLA correcto para el caso y tener cache local (offline) como plan B.

6

Seguridad en el Diseño

defensa en profundidad

Capas (ninguna basta sola)

App (secrets nunca en el bundle) → HTTPS/TLS → API (Auth + RLS) → DB (menor privilegio + backups cifrados).

Authn vs Authz

Authentication: quién eres (login, OAuth, magic link). Authorization: qué puedes hacer (permisos por fila). Error típico: validar solo el login y olvidar la autorización.

RLS como capa de autorización

El módulo 03 lo implementa; aquí la visión de diseño: RLS se evalúa en la DB (no en la app). Aunque roben un JWT, la policy sigue protegiendo. Cada policy usa auth.uid() (el sub del JWT de Supabase).

CREATE POLICY "read_own_drafts" ON posts
FOR SELECT USING (auth.uid() = user_id AND status = 'draft');

Principio de menor privilegio

QuiénPermisos correctos
Anon key en la appSolo lo público (RLS niega el resto)
Service role keyNunca en la app; solo Edge Functions/servidor
Edge FunctionsSolo las operaciones que necesitan
Storage bucketsBucket público vs privado + RLS en storage.objects

Checklist mínimo: ✅ HTTPS en todo · ✅ tokens en flutter_secure_storage · ✅ RLS en todas las tablas · ✅ service role solo en backend · ✅ .env en .gitignore · ✅ menor privilegio en roles.

Observabilidad y Resiliencia

medir, alertar, recuperarse

Los 3 pilares

PilarQué esPregunta que responde
LogsEventos discretos (JSON, con trace_id)¿Qué pasó?
MétricasNúmeros agregados (USE: Utilización, Saturación, Errores)¿Cuánto / con qué frecuencia?
TracingRecorrido del request por todos los componentes¿Dónde se tardó?

Alertas accionables (4 pasos)

1) Métrico correcto (error rate, latencia p95) · 2) Umbral realista · 3) Alerta con link al log/trace · 4) Solo lo que alguien puede arreglar.

ALERTA "Error rate GET /api/feed > 5% durante 5 min"
ACCIÓN: revisar Edge Function / query de feed / saturación de DB

Resiliencia (self-healing)

TécnicaQué hace
TimeoutsNingún request se cuelga para siempre
Retries + backoffReintenta esperando más cada vez (1s, 2s, 4s…)
Circuit breakerTras N fallos, falla rápido en vez de pegarle al servicio caído
FallbacksSi la fuente falla, sirve cache / datos locales

En Supabase los logs de Postgres, Auth, Realtime, Storage y Edge Functions ya son gestionados (dashboard + API). No montes un stack de observabilidad hasta que el tráfico lo justifique.

8

Offline-First y Sincronización

la red no es confiable

Los 4 niveles

NivelQué guarda
1. Lectura offlineCache de lo ya visto (feed cargado)
2. Escrituras offlineAcciones en cola local (like, mensaje)
3. Sync en backgroundLa cola se envía al reconectar
4. Conflict resolutionAmbos lados editaron lo mismo

Estrategia recomendada: optimistic UI + cola

1. Usuario da like → cola local + UI actualiza al instante
2. Sin red: queda "pending" en la cola
3. Al reconectar: se envía en orden con retries + backoff
4. Éxito → "synced" · fallo → reintento con límite

Conflictos: definirlos ANTES

PolíticaQué pasa
Last-write-wins (LWW)Gana el último updated_at. Simple; pierde trabajo.
Merge manualSe conservan ambos y el usuario decide
Por campoEl último cambio por cada campo

Por qué funciona con Supabase: Realtime empuja cambios remotos · RLS decide qué sincronizar · UUIDs como PK (sin colisiones de sync) · updated_at para LWW y delta sync. Diseño AP: disponible siempre, consistente eventualmente.

Casos Integradores (decisiones + CAP)

4 diseños resueltos

1 · Feed de Red Social (read-heavy)

DecisiónTrade-off
Cache-aside del feed (Redis)Primer acceso lento tras expiración
Postgres como fuente de verdadConsistencia fuerte; escala menor
CDN para mediaTTL/invalidación al borrar
Cache local Isar (offline)Sync = complejidad extra

CAP: AP (una foto "unos segundos tarde" no es crítico); el post en sí usa strong consistency para no perder publicaciones. Escala: ~1.7K QPS lectura, 10:1.

2 · Chat / Mensajería (write-heavy + realtime)

DecisiónTrade-off
Realtime (WebSocket) para entregarGestión de conexiones, límites
Insert en Postgres como "canal"Realtime depende de la DB
Cola + optimistic UIComplejidad de sincronización
UUIDs + LWW por updated_atIDs más largos

CAP: AP en la entrega percibida, pero el mensaje nunca se pierde: persistencia fuerte en el servidor. RLS crítico: leer solo si participas en la conversación.

3 · E-commerce Escalable (dinero + stock)

DecisiónTrade-off
Catálogo con cache-asideStock visible puede estar desfasado
Checkout transaccional (ACID)Checkout más lento que el resto
Edge Function para checkoutComplejidad de despliegue
Idempotencia en pagos—
 
// Evita el oversell (2 compradores, 1 unidad):
BEGIN;
SELECT stock FROM products WHERE id = $1 FOR UPDATE;  -- lock
-- stock >= qty ? resta + inserta order : error "sin stock"
COMMIT;

CAP: CP en checkout (prefiere rechazar antes que dejar pasar un oversell); catálogo AP.

4 · SaaS Multi-Tenant (aislamiento)

DecisiónTrade-off
Single Postgres + RLS como aisladorPolíticas complejas; riesgo si una falla
Roles por membresía (admin/member/viewer)Más SQL de policies
Cache namespaced por org_idInvalidar por tenant al escribir
Test de aislamiento en CISuite dedicada
 
CREATE POLICY "read_projects_of_my_orgs" ON projects
FOR SELECT USING (EXISTS (
  SELECT 1 FROM organization_members m
  WHERE m.org_id = projects.org_id AND m.user_id = auth.uid()
));

CAP: CP — la consistencia de datos de proyectos importa más que servir data eventual. Riesgo clave: noisy neighbor (un tenant saturado) → cuotas y rate limits.

Errores Comunes

FaseError típicoSolución
AlcanceDiseñar sin clarificar · olvidar el fuera de scopePreguntar usuarios/carga/latencia ANTES de dibujar

DatosNoSQL "por moda" · indexar todoRDBMS primero · índices solo para path reales

RealtimeWebSocket para todo · solo REST cuando piden realtimeÁrbol de decisión: polling → SSE → WS

ObservabilidadMétricas sin logs/traces · alertas por todoLos 3 pilares + alertas accionables
