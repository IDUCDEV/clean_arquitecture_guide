Filosofia y analogias (2 min)

Robert C. Martin · Uncle Bob

Clean Architecture = separar responsabilidades en capas concetricas. El nucleo (Domain) no depende de nada externo.

La analogia del restaurante

RestauranteCodigoCapa
RecetaEntity, UseCaseDOMAIN
CocinaModel, DataSourceDATA
MeseroCubit, StatePRESENTATION
Mesa/ClienteWidget, PageUI
AlmacenAPI, Base de datosEXTERNAL

La analogia del edificio de 4 pisos

Piso 4 (arriba): UI          — El cliente ve y toca
Piso 3:         Presentation — El mesero orquesta
Piso 2:         Domain       — El chef cocina (nucleo puro)
Piso 1 (abajo): Data         — La cocina accede a ingredientes

4 beneficios: Independencia de frameworks · Testable al 100% · Escalable y mantenible · Organizacion clara

El problema: codigo espagueti

Widget build(BuildContext context) {
  final response = await http.get(Uri.parse('https://api...'));  // HTTP en UI!
  final data = jsonDecode(response.body);                         // Parseo en UI!
  if (data['status'] == 200) { ... }                              // Logica en UI!
}

Todo mezclado: HTTP + parseo + logica + UI en un solo lugar. Clean Architecture resuelve esto.

Las 4 capas en detalle (3 min)

CapaContieneDepende deAnalogia
DomainEntity, Repository Interface, UseCaseSolo Dart puroReglas del ajedrez
DataModel, DataSource, RepositoryImplDomain (interfaces)Tablero fisico
PresentationCubit/Bloc, StateDomain (UseCases)Visor movil del tablero
UIWidgets, PagesPresentation (Cubit)Pantalla del telefono

Test de capa: Si el codigo puede vivir en un proyecto Dart sin Flutter → es Domain. Si no → es otra capa.

3 principios fundamentales

  • Capas: Cada archivo pertenece a UNA sola capa
  • Regla de dependencia: Las flechas van de afuera hacia adentro (UI → Presentation → Domain ← Data)
  • Abstracciones: Domain usa interfaces/abstract classes; Data las implementa

Flujo de llamada

UI(UserWidget) → Cubit.fetchData() → UseCase.call()
  → Repository.getData() [interface en Domain]
  → RepositoryImpl [en Data, implementa la interface]
  → DataSource.fetch() [API/DB]
  → Modelo → Entity → Either<Failure, Entity> → Cubit → UI

Flujo de datos y manejo de errores (3 min)

Cada operacion CRUD sigue una forma de U: baja por las capas y sube de vuelta.

USUARIO toca boton
  → Widget: context.read<UserCubit>().fetchUsers()
  → Cubit: emit UserLoading(); result = await useCase();
  → UseCase: valida reglas, llama repository
  → RepositoryImpl: decide remote vs local
  → DataSource: ejecuta HTTP/DB query
  → Modelo: UserModel.fromJson() → toEntity() → UserEntity
  → Either<Failure, UserEntity> sube de vuelta
  → Cubit: emit UsersLoaded(users) o UserError(message)
  → UI: BlocBuilder reconstruye el widget

Manejo de errores: Exception vs Failure

ConceptoCapaQue esEjemplo
ExceptionDATAError tecnico (no llega al usuario)ServerException, CacheException
FailureDOMAINError amigable (llega al usuario)ServerFailure, CacheFailure, NetworkFailure

Cadena de errores

DataSource lanza Exception
  → RepositoryImpl catch(Exception) → convierte a Failure
  →返回 Either<Failure, T> (Left)
  → UseCase recibe Failure
  → Cubit emite UserError(message)
  → UI muestra SnackBar amigable

Nunca dejes que una excepcion tecnica (HTTP 500, timeout, SQL) llegue a la UI. Siempre se convierte en Failure primero.

Domain Layer — El nucleo puro (3 min)

Contiene 3 componentes: Entity, Repository Interface, UseCase. Sin dependencias externas.

Entity

class User extends Equatable {
  final String id;
  final String name;
  final String email;
  final bool isActive;
  final DateTime createdAt;

  const User({required this.id, ...});

  User copyWith({String? name, ...}) => User(id: id, name: name ?? this.name, ...);

  bool get isNew => DateTime.now().difference(createdAt).inDays < 7;

  @override
  List<Object?> get props => [id, name, email, isActive, createdAt];
}

Repository Interface

abstract class UserRepository {
  Future<Either<Failure, List<User>>> getUsers();
  Future<Either<Failure, User>> getUser(String id);
  Future<Either<Failure, User>> createUser(User user);
  Future<Either<Failure, void>> deleteUser(String id);
}

UseCase

class GetUsers extends UseCase<List<User>, NoParams> {
  final UserRepository repository;
  GetUsers(this.repository);

  @override
  Future<Either<Failure, List<User>>> call(NoParams params) async {
    return await repository.getUsers();
  }
}

Future<Either> vs TaskEither

AspectoFuture<Either>TaskEither
ComplejidadBaja (familiar)Alta (funcional)
ComposicionLimitadaEncadenable con .andThen()
Ideal paraEquipos junior/midEquipos avanzados

El modulo usa Future<Either> por accesibilidad.

RepositoryImpl — Logica Online/Offline

class UserRepositoryImpl implements UserRepository {
  final UserRemoteDataSource remoteDataSource;
  final UserLocalDataSource localDataSource;
  final NetworkInfo networkInfo;

  @override
  Future<Either<Failure, List<User>>> getUsers() async {
    if (await networkInfo.isConnected) {
      try {
        final models = await remoteDataSource.getUsers();
        await localDataSource.cacheUsers(models);  // Guardar en cache
        return Right(models.map((m) => m.toEntity()).toList());
      } on ServerException {
        return Left(ServerFailure());
      }
    } else {
      try {
        final cached = await localDataSource.getCachedUsers();
        return Right(cached.map((m) => m.toEntity()).toList());
      } on CacheException {
        return Left(CacheFailure());
      }
    }
  }
}

Presentation + UI Layer — El estado y la vista (3 min)

States

abstract class UserState extends Equatable {}
class UserInitial extends UserState { ... }
class UserLoading extends UserState { ... }
class UsersLoaded extends UserState {
  final List<User> users;
  const UsersLoaded(this.users);
}
class UserError extends UserState {
  final String message;
  const UserError(this.message);
}

Cubit

class UserCubit extends Cubit<UserState> {
  final GetUsers getUsers;
  final GetUser getUser;
  final CreateUser createUser;
  final DeleteUser deleteUser;

  UserCubit({required this.getUsers, ...}) : super(UserInitial());

  Future<void> loadUsers() async {
    emit(UserLoading());
    final result = await getUsers(NoParams());
    result.fold(
      (failure) => emit(UserError(_mapFailure(failure))),
      (users) => emit(UsersLoaded(users)),
    );
  }
}

UI con flutter_bloc

BlocProvider(
  create: (context) => sl<UserCubit>()..loadUsers(),
  child: BlocBuilder<UserCubit, UserState>(
    builder: (context, state) {
      if (state is UserLoading) return CircularProgressIndicator();
      if (state is UserError) return Text(state.message);
      if (state is UsersLoaded) {
        return ListView.builder(
          itemCount: state.users.length,
          itemBuilder: (ctx, i) => UserTile(user: state.users[i]),
        );
      }
      return SizedBox();
    },
  ),
)

Regla: UI solo muestra datos y captura eventos. Nunca logica de negocio, ni llamadas HTTP, ni parseo de JSON.

Inyeccion de Dependencias con GetIt (2 min)

GetIt es un Service Locator: registra instancias y las entrega cuando se necesitan.

3 metodos de registro

MetodoCUANDO se creaIdeal para
registerLazySingletonPrimera vez que se pideRepositorios, DataSources (recomendado)
registerSingletonAl registrarloConfig, servicios globales
registerFactoryCada vez que se pideCubits (nueva instancia por uso)

Estilo Manual (recomendado)

final sl = GetIt.instance;

Future<void> init() async {
  // ── Externos ──
  sl.registerLazySingleton(() => SupabaseClient());
  sl.registerLazySingleton(() => InternetConnection());

  // ── Core ──
  sl.registerLazySingleton(() => NetworkInfoImpl(sl()));

  // ── DataSources ──
  sl.registerLazySingleton<UserRemoteDataSource>(
    () => UserRemoteDataSourceImpl(sl()),
  );
  sl.registerLazySingleton<UserLocalDataSource>(
    () => UserLocalDataSourceImpl(),
  );

  // ── Repositories ──
  sl.registerLazySingleton<UserRepository>(
    () => UserRepositoryImpl(
      remoteDataSource: sl(),
      localDataSource: sl(),
      networkInfo: sl(),
    ),
  );

  // ── UseCases ──
  sl.registerLazySingleton(() => GetUsers(sl()));
  sl.registerLazySingleton(() => CreateUser(sl()));

  // ── Presentation ──
  sl.registerFactory(() => UserCubit(getUsers: sl(), createUser: sl()));
}

Estilo Injectable (proyectos grandes)

Usa anotaciones (@lazySingleton, @injectable) + build_runner. Requiere: injectable, injectable_generator.

Regla: Empieza manual. Cambia a injectable cuando el service_locator.dart tenga +200 lineas.

SOLID en Dart/Flutter + Anti-patrones (3 min)

Los 5 principios SOLID

#PrincipioReglaEjemplo en Dart
SSingle ResponsibilityUna clase, una razon para cambiar CreateUserUseCase (no UserManager)
OOpen/ClosedAbierto a extension, cerrado a modificacion Abstract class + implementaciones
LLiskov SubstitutionSubtipos deben ser sustituibles Ambos implementan Shape (no hereda Rectangle→Square)
IInterface SegregationInterfaces pequenas y especificas UserReader + UserWriter (no UserRepository gigante)
DDependency InversionDepender de abstracciones, no concreciones Interface + inyeccion + GetIt

Los 8 anti-patrones

#Anti-patronProblemaSolucion
1God ClassUna clase hace todoSeparar por responsabilidad
2Dependencia invertida (mal)Domain depende de Data/PresentationFlechas solo hacia Domain
3Repository de papelRepository sin logica, solo passthroughAgregar logica o fusionar con UseCase
4Estado monoliticoUn solo State con 10+ camposDividir por dominio o usar multiples Cubits
5UseCase castradoUseCase solo delega sin logicaAgregar regla de negocio o fusionar
6Map hellMap<String, dynamic> sin tiposSiempre usar Modelos tipados
7Herencia infinita5+ niveles de abstraccionesComposicion sobre herencia
8Callback hellCallbacks anidados profundosasync/await + manejo de errores

Test rapido: Si tu archivo tiene +300 lineas, si un UseCase solo delega, o si un State tiene +10 campos → probablemente tienes un anti-patron.

Cuando SI y cuando NO usar Clean Architecture (2 min)

El spectrum de complejidad

Script → Prototipo → App Simple → App Compleja → Enterprise
   ↓         ↓            ↓              ↓              ↓
 Nada    setState()    Cubit+Repo    Clean Arch    Clean+DDD+BLoC

Cuando SI usar

  • 10+ features
  • 3+ desarrolladores
  • Vida util de 2+ anios
  • multiples fuentes de datos
  • Testing exhaustivo
  • Dominio complejo

Cuando NO usar

CasoAlternativa
Prototipo / MVPsetState() + http
App de una pantallaCubit simple
Script / herramientaSin arquitectura
HackathonLo que funcione
UI-only appWidgets + setState
POC internoCubit + Repository simple

Senales de over-engineering

SenalAccion
Mas archivos que featuresEliminar abstracciones innecesarias
UseCases que solo deleganFusionar con Repository
Interfaces con una sola implementacionEliminar la interfaz
3+ niveles de abstraccionAplanar la jerarquia
Tardas 30+ min en agregar una featureSimplificar la arquitectura

Regla practica: 3+ features = Clean Architecture. Menos = Cubit + Repository simple. Desechable = lo que funcione.

Conclusion

Clean Architecture es una herramienta, no un dogma. Usala cuando el proyecto lo necesite. La clave es:

  • Domain puro: sin dependencias externas
  • Flechas hacia adentro: Domain nunca sabe de UI ni Data
  • Interfaces en Domain, implementaciones en Data
  • Errors: Exception (DATA) → Failure (DOMAIN) → UI amigable
  • GetIt para DI: manual para empezar, injectable para escalar
  • SOLID como guia, no como religion
Tiempo de lectura del resumen: ~25 min · Clean Architecture es un camino, no un destino.
