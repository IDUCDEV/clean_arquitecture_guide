Conventional Commits (5 min)

Especificacion v1.0.0

Conventional Commits = convencion ligera para mensajes de commit que permite generar CHANGELOGs y versionado semantico automatico.

Formato del mensaje

<tipo>[<ambito opcional>][<! opcional>]: <descripcion>

[cuerpo opcional]

[nota(s) al pie opcional(es)]

Tipos principales

TipoQue haceVersion SemVer
featNueva funcionalidadMINOR (1.0.0 → 1.1.0)
fixCorreccion de bugPATCH (1.0.0 → 1.0.1)
BREAKING CHANGECambio incompatibleMAJOR (1.0.0 → 2.0.0)

Tipos adicionales

TipoCuando usarEjemplo
buildBuild systembuild: upgrade gradle a 8.0
choreMantenimientochore: limpiar dependencias
ciCI/CDci: agregar step de codegen
docsDocumentaciondocs: actualizar README
perfRendimientoperf: cachear consultas
refactorRefactorizarrefactor: extraer widget
styleFormatostyle: dart format
testTeststest: cubrir caso borde

Reglas de oro

  • Imperativo presente ("agregar", no "agregue")
  • Sin punto final
  • Maximo 72 caracteres
  • Primera letra minuscula
  • Ambito opcional: feat(auth): ...

Breaking Changes

# Opcion 1: ! despues del tipo
refactor!(auth): cambiar respuesta de login a JWT

# Opcion 2: BREAKING CHANGE en el pie
feat: migrar de SQLite a Isar

BREAKING CHANGE: Se elimino la base de datos local.

Ejemplo real: feat(raffles): agregar filtro por fecha → version 1.0.0 → 1.1.0. Si incluye ! o BREAKING CHANGE → 1.1.0 → 2.0.0

2

Husky + lint-staged (3 min)

Hooks de Git

Husky ejecuta scripts automaticos en hooks de Git. lint-staged ejecuta comandos SOLO en archivos staged.

Los 3 hooks principales

HookCuando se ejecutaQue hace
pre-commitAntes del commitFormateo + analisis (lint-staged)
commit-msgDespues del mensajeValida formato (commitlint)
pre-pushAntes del pushEjecuta tests completos

Configuracion lint-staged para Flutter

"lint-staged": {
  "*.dart": [
    "dart format --set-exit-if-changed",
    "flutter analyze --fatal-infos"
  ],
  "*.{yaml,json}": ["prettier --write"]
}

Emergencias: git commit --no-verify -m "fix: hotfix critico" salta los hooks temporalmente.

3

Commitizen + commitlint (3 min)

Asistentes de commit

Commitizen = CLI interactivo que genera commits validos. commitlint = linter que valida mensajes.

Flujo con Commitizen

$ npx cz

? Selecciona el tipo de cambio: feat
? Alcance: raffles
? Descripcion: agregar filtro por fecha
? Breaking change: No

→ feat(raffles): agregar filtro por fecha

Reglas de commitlint

ReglaValorDescripcion
type-enum[2, 'always', [...]]Tipos permitidos
type-empty[2, 'never']Tipo requerido
subject-empty[2, 'never']Descripcion requerida
header-max-length[2, 'always', 72]Maximo 72 caracteres
subject-full-stop[2, 'never', '.']Sin punto final

Standard Version (CHANGELOG automatico)

# Ejecutar release
npm run release

# Esto genera:
# - CHANGELOG.md actualizado
# - package.json con version bump
# - Commit con los cambios
# - Tag v1.2.0

Tabla resumen: Commitizen (escribe) + commitlint (valida) + standard-version (libera) = flujo completo.

4

FVM: Flutter Version Management (2 min)

Multi-version Flutter

FVM permite que cada proyecto tenga su propia version exacta de Flutter.

Comandos esenciales

ComandoQue hace
fvm install 3.24.0Instala una version
fvm use 3.24.0Configura el proyecto
fvm flutter pub getUsa la version del proyecto
fvm listLista versiones instaladas
fvm currentVersion actual del proyecto

Archivos clave

.fvm/flutter_sdk_version   # Version configurada (SE COMITA)
.fvm/flutter_sdk            # SDK instalado (SE IGNORA en .gitignore)

VS Code: Configurar "dart.flutterSdkPath": ".fvm/flutter_sdk" en .vscode/settings.json para que use la version correcta automaticamente.

Ramas, Git Flow y Versionado (5 min)

Conventional Branch + SemVer 2.0.0

Conventional Branch = nomenclatura estructurada para ramas Git.

Prefijos de ramas

PrefijoPropositoEjemplo
mainRama principal (produccion)main
feature/Nuevas funcionalidadesfeature/agregar-login
bugfix/Corregir erroresbugfix/corregir-crash
hotfix/Correcciones urgenteshotfix/parche-seguridad
release/Preparar liberacionrelease/v1.2.0
chore/Tareas sin codigochore/actualizar-deps

Git Flow simplificado

main ──── M1 ────────── M2 ────────── M3 (produccion)
          │              │              │
develop ─ D1 ─ D2 ─ D3 ─ D4 ─ D5 ─ D6 (integracion)
          │    │         │         │
feature/  │    └─ feat1   │         └─ feat3
          │               └─ feat2

Versionado Semantico (SemVer 2.0.0)

VersionCuando incrementarEjemplo
Major (X)Cambios incompatibles1.0.0 → 2.0.0
Minor (Y)Nueva funcionalidad1.0.0 → 1.1.0
Patch (Z)Correccion de bug1.1.0 → 1.1.1

Flujo completo

1. Crear rama feature desde develop
2. Commits con feat/fix (Conventional Commits)
3. PR a develop + code review
4. Merge a develop
5. Crear release/X.Y.Z desde develop
6. standard-version genera CHANGELOG + bump
7. Merge a main + tag vX.Y.Z
8. Deploy a Play Store / App Store

Hotfix: Si hay bug critico en produccion → crear hotfix/ desde main → fix → merge a main Y develop → tag vX.Y.Z+1

Conclusion

El flujo de trabajo profesional en equipo se basa en convenciones claras:

  • Conventional Commits para mensajes consistentes
  • Husky + lint-staged para calidad automatica
  • Commitizen + commitlint para commits validos
  • FVM para versiones de Flutter consistentes
  • Git Flow + Conventional Branch para ramas organizadas
  • SemVer para versionado predecible
  • standard-version para CHANGELOG automatico
Tiempo de lectura del resumen: ~20 min · El camino hacia un flujo de trabajo profesional empieza con convenciones claras.
